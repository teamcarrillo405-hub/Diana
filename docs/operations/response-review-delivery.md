# Course Practice response review delivery

Status: **disabled pending deployment and human operations**. The three forward migrations implement a review queue, operator-keyed packet seal and one-use educator invitations. None has been applied to shared staging or provisioned with a real key or real adult/reviewer verification in this workstream. Both `DIANA_RESPONSE_REVIEW_ENABLED` and the private database gate default off. The HTTP route returns 503 before reading private data; direct authenticated review RPCs cannot deliver sealed responses while the database gate is off. No real educator ratings have been collected.

## Access contract

- An authenticated **operator-verified adult record owner** may explicitly request review of one confirmed Diana-authored Course Practice answer at its current revision. The HTTP request includes `consent: true` and two opaque invitation IDs chosen by safe educator labels. A trusted operator provisions each invitation for a specific owner and subject; the named adult educator accepts it before use. The database resolves two distinct current educators and atomically binds each invitation to one request. The old raw-reviewer-ID request RPC is no longer executable by authenticated users. A draft cannot be listed to reviewers, read or rated before sealing. Profile age alone is self-declared and is insufficient: the invitation path also requires a current operator-maintained adult eligibility record for the owner and both reviewers. No such real records have been provisioned.
- Only the two named educators can read the sealed packet while their invitation, operator adult eligibility, credential, subject permission, request and owner response revision remain current. The database returns the selected answer, modality, support count, activity version and request metadata. It never returns other notebook observations, PDF contents, recognition evidence or the student's user ID. The route rebuilds the signed packet against the current authored catalog before returning it. HTTP DTOs omit other educator UUIDs, but direct authenticated database RPCs can reveal stable reviewer UUIDs; this is **not** an anonymity guarantee.
- A named educator may submit a rating and later correct it up to five total submissions for that request. The HTTP form sends criterion judgments and response selections; the server supplies the current reviewer identity/credential, packet/rubric hashes, ID and time. Before writing, the database requires exact bindings, ordered criterion IDs, bounded scores and rationales, and exact UTF-16 evidence spans within the sealed answer. Extra or missing fields are rejected before consuming a submission. Every accepted submission is retained in an append-only audit history; a monotonic submission order makes the latest selection deterministic. Only that educator's latest rating is evaluated. The owner may revoke access at any time. An owner-only report recalculates agreement from two current reviewers and the exact packet/rubric hashes. The educator's no-conflict declaration is self-attested; an operator must check independence in the real review program. This is descriptive feedback, not a course grade or a learning-effect measure. Revocation, credential lapse and response revision changes make delivery unavailable.
- The SQL functions keep invitation and adult-eligibility tables and the seal key inaccessible to authenticated direct reads and writes. A private verifier checks a server HMAC over the exact database-generated packet challenge, owner, record, revision, authored activity version, response bytes, packet/rubric hashes, ordered criterion IDs and current invitation/credential/adult-eligibility revisions before every read or rating. A stored seal and its request bindings become immutable. Revoking and restoring a permission does not revive the old seal. The route additionally tests a fresh challenge against its configured key on each request.

The first migration alone grants no authenticated review RPC access. Do not apply this chain to shared staging casually.
2. Provision two independent secrets out of source control. `DIANA_RESPONSE_REVIEW_BLINDING_KEY` needs at least 32 characters. `DIANA_RESPONSE_REVIEW_SEAL_KEY_HEX` must be 64–128 lowercase hex characters representing 32–64 random bytes. Insert those same seal bytes into the singleton `diana_private.learning_response_review_seal_key` through a controlled operator channel. Keep both secrets out of source, logs, fixtures and browser code. Rotation invalidates open requests unless a versioned migration retains old keys; revoke or complete open requests first.
3. A trusted operator must verify adult eligibility and educator identity/qualifications through a documented method, store non-sensitive evidence references and expiration in `learning_response_review_adult_eligibility`, provision current `learning_editor_access`, then issue an owner/subject-scoped invitation. Only the named educator can accept it. No ID image or DOB scan belongs in these tables. The current code and synthetic tests do not establish that any real person has been verified or that an educator agreed to a service level. Do not automatically match a student with a reviewer.
4. In an isolated PostgreSQL 16 database, load the real problem-record migration and all three review migrations with the real `profiles.user_id` shape, then run `scripts/learning/test-response-review-sealed-real-schema.sql` and `scripts/learning/test-response-review-invitations-real-schema.sql`. The September 26 local runs passed direct-RPC ACL, seal, one-use invitation, age/credential/revision drift, rating/report, revocation/expiry and database-gate OFF-after-seal cases. The synthetic rows/key were rolled back and the local cluster removed. This is a database contract test, not real educator review or live HTTP/database integration acceptance.
5. For minors, design and independently approve a separate institution/guardian sharing permission workflow before any student-response review. The adult-only route is not a workaround for that requirement.
6. Establish retention, deletion, notification, conflict-of-interest and educator-response service procedures before production availability. After key readiness, consent UX, reviewer provisioning and owner-approved rollout, enable the service-role-controlled `diana_private.learning_response_review_feature_gate.enabled` **and** set `DIANA_RESPONSE_REVIEW_ENABLED=true`. The DB gate starts OFF and only `service_role` may read/update it. A missing/mismatched key or DB gate OFF keeps the HTTP route at 503. For emergency shutdown, turn the DB gate OFF first: it stops direct RPC reads/ratings even for already sealed requests; then turn the HTTP flag OFF. Re-enabling the DB gate does not restore revoked, expired or changed permissions. The endpoint makes no promise that an educator will respond.

## API contract (disabled by default)

- `GET ?invitations=1&role=owner|reviewer` lists scoped safe invitation labels and opaque IDs. `POST` with `{ "action":"accept", "invitationId":"..." }` lets the named educator accept a one-use invitation.
- `POST /api/learning/response-review` with `{ "action":"request", "recordId":"...", "revision":2, "invitationIds":["...","..."], "consent":true }` creates and seals one eligible adult-owner request. If sealing fails, the route revokes the unusable draft. A claimed invitation cannot be reused for another request.
- `POST` with `{ "action":"revoke", "requestId":"..." }` revokes access.
- `GET ?role=owner|reviewer` lists scoped sealed request metadata. `GET ?id=...` returns a subject-checked packet to the owner or named reviewer, with other reviewer IDs removed from the HTTP response. Only the owner receives an agreement report when ratings exist.
- `POST` with `{ "action":"rateDraft", "requestId":"...", "noConflict":true, "criteria":[...] }` accepts ordered judgments. The server constructs the versioned `responseAssessmentSchema` using the authenticated reviewer's current self-only credential and sealed packet. The database revalidates exact evidence spans and current permission. The owner can refresh a descriptive report; the reviewer page supplies response selections through a read-only textarea whose offsets use UTF-16 units.

No API action invokes an LLM, exports training data, sends a message to an educator, or changes automatic knowledge estimates.
